# ai-software-factory-infra

What the cluster is: OpenTofu for Hetzner Cloud servers, Talos machine
configs, Flux-managed platform manifests. Design lives in the
ai-software-factory repo. Human-only repository, agents never write here.

## Flux layout

Flux v2.9.5 is bootstrapped against
`https://git.aisoftwarefactory.world/sf/ai-software-factory-infra`,
sync path `clusters/sf`:

- `clusters/sf/flux-system/` — Flux components and the flux-system sync,
  written by `flux bootstrap`.
- `clusters/sf/platform.yaml` — the Kustomization that owns the platform
  tree; `clusters/sf/kustomization.yaml` is the sync build root.
- `clusters/sf/factory.yaml` — the GitRepository `factory-code` (the code
  repo, secret `forgejo-pat`) and the Kustomization `factory` that applies
  the code repo's `k8s/` tree (namespace `factory`, prune on, after
  `platform`).
- `clusters/sf/notifications.yaml` — the Provider `forgejo-infra` (type
  `gitea`, secret `forgejo-commit-status`) and its Alert: every
  reconciliation of the Kustomizations `flux-system` and `platform` posts
  a commit status on the revision it applied, contexts `flux/flux-system`
  and `flux/platform` (success, or failure on an error), which the infra
  project's chain requires. The contexts name the Kustomization only,
  through `commitStatusExpr`: Flux's default ends in the Provider's UID,
  which a rebuild changes. The infra project file's `chain.requires` and
  the Alert's `eventSources` change together: a Kustomization renamed in
  or removed from the Alert posts no more, and the head stalls by design.
- `k8s/platform/` — the platform tree: chart sources, Gateway API edge,
  cert-manager and Forgejo HelmReleases, CNPG, local-path (and its class
  `factory-cache`: the per-project Go build and npm caches of agent
  sessions and CI runs, a directory per claim name under
  /var/lib/factory-cache on EPHEMERAL, not the noexec user volume, that
  Retain keeps; only factoryd may claim it; local-path's `setup.sh`
  prunes them at each claim: a cache unclaimed for 14 days goes, one
  above 10 GiB loses its files unchanged for 3 days; tested by
  `scripts/cache-setup-test/test.sh`), and the
  CoreDNS Corefile. The Corefile's rewrite sends in-cluster git DNS to
  the gateway Service; prune is on, so deleting coredns.yaml from the
  tree deletes the rewrite and re-breaks the Flux sync. From here on,
  platform changes ship as commits to this tree and Flux applies them;
  nothing is applied by hand.

## Configuration

`factory/` is factoryd's configuration (ruling 183), read straight from
this repository's `main`; no ConfigMap, no custom resource. Git is the
editing surface, the console shows it read-only.

- `policy.yaml`: per-task default and maximum budget and the per-day cap
  over all tasks (UTC day); `limits` (`sessions`, the round cap;
  `agent_time`, the agent's working time across a task's sessions;
  `supervisor_calls` per session; `supervisor_timeout` per supervisor or
  review call, at most 15m; `stronger_after`, the returns from one stage
  that keep the model; `steps`, the model turns per agent session, 200
  when absent; `nudge_after` and `nudges`, the loop nudge: that many
  identical tool calls in a row get the running session a message to
  change approach, that many times per repetition, 3 and 1 when absent;
  `same_call`, the identical tool calls per session that trip the
  same_call detector once the nudges are spent, above `nudge_after`, 4
  when absent); the capability classes (the model aliases and
  tools a task class may use: a paid tool with per-task `max_requests`
  and `max_eur`, a free one, `escalate_to_human` and the commissioning
  tools, as `{}`; a tool no class of the task lists is refused, ruling
  132); `prices`, the tool prices no provider API reports (Firecrawl's
  EUR per credit, Replicate's EUR per second by hardware SKU and the SKU
  of each usable model, fal's megapixel bound), each with its source
  URL; `risk`, the rules that classify an agent pull request by its
  changed paths (ordered globs to a class, most severe class wins;
  `forbidden` fails the task, `requires_approval` waits for a human
  before `factory-merge` merges; `migration: true` flags schema
  migrations for the human's review); `envelope_default`, the resource
  envelope of a project whose file sets none; `project_default`, the
  quota and standing block of one that sets none (both are also caps:
  stricter wins, a project file may only tighten them, and a looser
  value or an unlisted server type rejects the commit); and
  `approvers` (ruling 128), the Forgejo users who may authorize spend in
  the console; a merge approver must also be on main's approvals
  whitelist; `link_hosts`, the hosts (with their subdomains) links in
  agent-written text factoryd posts on Forgejo may point at besides the
  Forgejo host and the project's own hosts, any other link defanged. A Replicate model runs only once it is listed under
  `prices.replicate.models`.
- `commands.yaml` (optional): the chat's commands (roadmap 239), each a
  `name` the member types after a slash, the `words` the palette shows
  and the `message` the chat sends for it. A name is a lowercase letter,
  then lowercase letters, digits and dashes, at most 24, and never
  `compact` or `new`, the chat's own commands.
- `processes/<name>.yaml`: the processes a project's cards pass
  (rulings 206, 208), four blocks each: `lanes` (backlog, ready and an
  optional plan, each starting lane naming a class of `policy.yaml` and
  who may move a card into it), `dependencies` (only with a plan lane),
  `stages` (the stages a task's work passes, in order, each with
  `on_findings: agent | human | fail`, `enabled` and an optional `when:
  outsider`, ruling 177) and `merge: {queue: none | project}`.
  `maintenance` is the factory's flow for existing code, `spec` builds
  from a spec. A class's `session` (`code`, `report`, `plan`) chooses the
  program its tasks run. `factoryd config explain <process> <card kind>`
  prints the path of a card kind through a process.
- `projects/<name>.yaml`: one file per project, the only place its
  settings live (rulings 146, 179, 183): repository, merge rule,
  `objects: factory | seed` (who makes the repository objects:
  factoryd's registration, or this repository and the seed; of a seed
  project factoryd keeps the labels and, for agents coder, the bot's fork,
  and only reports its webhook and namespace labels), `agents: coder | none` (`none`: every
  issue and alert goes to the human lane, `POST /tasks` answers 422),
  `process` (for agents coder, the name of a file under `processes/`),
  `template` (a factory project's, the name of a directory under
  `templates/`: registration seeds the empty repository's `main` with it),
  notify, namespaces, environments, quota, secrets, `envelope` (the task
  block) and `standing`. `messengers: false` (roadmap 145) keeps the
  project's notifications off Telegram and Discord. A seed project names the seeded secrets
  factoryd reaches it with in `tokens` (`read`; `actions`, with which the
  chain poller reads its push runs, and for agents coder its CI; `merge`
  for agents coder; values `forgejo-ci-registrar`, `forgejo-merge`,
  `forgejo-config`, never `forgejo-projects`; `gate`, only
  `forgejo-gate`, the merge gate's approval; `chat`, only `forgejo-chat`,
  the project agent's own identity in a turn no member started); a
  factory project's are registration's. The code repository's file lists the namespace
  `factory`, factoryd's own: that makes it the factory's own project
  (its rolls, its CI runs, the console's login). A new factory project:
  add its file (the console's new-project button files it as a pull
  request); once it is on `main`, factoryd's reconcile registers it with
  the Forgejo site admin factory-admin's login from OpenBao
  (`factory/forgejo-admin`, ruling 212); `factoryd register-project --name <name> --rotate` mints
  its tokens again. The console shows every project and envelope
  read-only with a link here.
- `templates/<name>/`: the files registration commits as a new factory
  project's first commit on `main` (stage11-design.md section 6), rendered
  with Go's `text/template` between `[[` and `]]` (so `${{ }}` of Actions
  passes through; a file never writes `[[` or `]]` otherwise) with the
  project's `.Name`, `.Repository`, `.Image` and `.Namespaces` (namespace
  by environment path). Every template carries `.forgejo/workflows/pr.yml`,
  `.forgejo/workflows/ci.yml`, `.forgejo/roll.sh` and
  `deploy/base/kustomization.yaml`; the check renders each file with sample
  data. `ts-go` is a TypeScript single-page frontend and a Go API in one
  image: a minimal app that passes `bash check` (the repository's one
  check, which CI and the agents run), builds its image and deploys to
  staging as seeded; its `AGENTS.md` names the layout its CI relies on.
- `schema/`: the JSON Schemas `factoryd schema --out factory/schema`
  generates from factoryd's Go types. Each YAML file's first line
  references its schema (`# yaml-language-server:
  $schema=schema/policy.schema.json`, `../schema/project.schema.json`
  under `projects/`, `../schema/process.schema.json` under `processes/`), so an editor with the YAML language server
  completes keys, lists every enumerated value and marks mistakes.

To change it: edit, run `factoryd config check factory` (the image's
binary, or `go run ./cmd/factoryd config check <path>` in the code
repository), commit, push to main. factoryd polls the head of `main`
every 30 s with the read-only `forgejo-config` token, and records a
valid tree as an immutable `policy_versions` row keyed by the commit;
the gateway enforces the new version from Postgres within 30 s more and
names it in every audit row. A task pins the version its workflow
started under: its session cap, agent time and stronger rung, and in
every session, gate-supervisor call and model review the agent time,
`steps`, the loop nudge, `supervisor_calls`, `supervisor_timeout` and the `no_write` detector
come from that version, and so do the activity bounds of those three.
Everything else is read from the version in force when used: the risk
rules, the factoryd model aliases, what the gateway enforces (classes,
tool caps, prices, the day cap), the budget at intake, the approvers,
the other activities' bounds and the envelope defaults. An
invalid commit (unknown key, second YAML
document, a value outside its enumeration, a missing required key, a
missing schema header, an unknown file, a `coder` class that leaves out
a model of factoryd's ladder `MODEL`, `STRONGER_MODEL`) is logged
(`CONFIG REJECTED`), the previous version stays in force, and factoryd
files one issue here per refused commit (a human-lane task, source
`config`) with an alerts row of kind `config_rejected`; the next valid
commit comments on it, closes it, ends the task and judges the alert
real. Ten failed reads in a row (a revoked `forgejo-config` token,
Forgejo unreachable; about five minutes) raise one `config_rejected`
alert of source `read`, without an issue. The workflow
`.forgejo/workflows/config-check.yml` runs the same check on every push
to main and is red for such a commit; it also fails when `schema/`
differs from what the pinned factoryd generates. It runs on the org
runner (`ubuntu-latest`): this repository is human-only, so the
privileged runner only ever runs what a human pushed to `main`, the
same trust as the code repository's main CI. Its `FACTORYD_IMAGE`
digest follows factoryd: every factoryd roll updates it (and
`factory/schema/` when the types changed). `day_eur: 0` stops all spend.
Every activation is an append-only `policy_activations` row, so the
history of what was in force when stays in Postgres. `GET /policy` on
factoryd and the console's Policy page show the version in force.

## Accounts (ruling 229)

No tool of the factory logs in as a human, so sebastian may switch TOTP on
at any time: Forgejo then refuses his password's basic auth on the API and
on git over https without the `X-Forgejo-OTP` header, and nothing else
notices.

- `sebastian`: the human, a site admin, password `FORGEJO_ADMIN_PASSWORD`
  in `.env.seed`, used by no tool. `scripts/seed-secrets.sh` creates the
  account only when it is missing and never touches it otherwise; a reset
  of his password is factory-admin's `PATCH /api/v1/admin/users/sebastian`
  by hand.
- `factory-admin`: the machine admin, a site admin the chart makes at
  Forgejo's start from `forgejo-admin-secret` (password
  `FORGEJO_FACTORY_ADMIN_PASSWORD`, synced at every start). The seed
  scripts, the CronJobs `console-oauth` and `push-mirrors`, and factoryd's
  registration (OpenBao `factory/forgejo-admin`) log in as it; it owns the
  console's OAuth app `factory-console`, Flux's token and the code
  repository's registry token `factory-registry` (`write:package`, main
  CI's Actions secrets). The hand-made tokens of the Rebuild (`runner-init`
  in step 6; `forgejo-ci-registrar`, `forgejo-ci-org-read`,
  `forgejo-projects` in step 8) are minted with its basic auth
  (`FORGEJO_FACTORY_ADMIN_PASSWORD`) and `?sudo=`.
- `controller`: the controller's own account, password
  `FORGEJO_CONTROLLER_PASSWORD`, no admin: a write collaborator on `sf`'s
  three repositories (`scripts/seed-secrets.sh`; Flux's commit statuses
  on this repository post with its token `forgejo-commit-status`), on code `main`'s push and
  approvals whitelists and infra `main`'s push and merge whitelists
  (ruling 239), and a policy approver, so factoryd's reconcile
  makes it a writer and approver on every factory project. The
  controller's scripts, console login and git pushes use it.
- The bots (`factory-agent`, `factory-merge`, `factory-gate`,
  `factory-chat`, `factory-ci`, `factory-projects`, `factory-config`,
  `factory-registry-read`, `ci-<project>`) have random passwords nobody
  keeps and tokens minted with `?sudo=`.

`scripts/seed-secrets.sh` appends `FORGEJO_FACTORY_ADMIN_PASSWORD` and
`FORGEJO_CONTROLLER_PASSWORD` to `.env.seed` when they are missing (32
random hex characters, never printed).

## The merge bot (ruling 109)

An approved agent pull request is merged by factoryd's `Merge` activity as
the dedicated Forgejo user `factory-merge`, never by the agent's bot. At
full auto, when the merge gate decides that an agent pull request merges
without a human, the approval comes from a second bot, `factory-gate`
(ruling R59), and the merge still comes from `factory-merge`.
Forgejo enforces the approval: `main` of `sf/ai-software-factory-code`
carries exactly this protection (branch protection `main`, set through
`PATCH /repos/sf/ai-software-factory-code/branch_protections/main`):

| field | value |
|---|---|
| `enable_push`, `enable_push_whitelist` | true |
| `push_whitelist_usernames` | `[sebastian, controller]` |
| `enable_merge_whitelist` | true |
| `merge_whitelist_usernames` | `[sebastian, factory-merge]` |
| `enable_approvals_whitelist` | true |
| `approvals_whitelist_username` | `[sebastian, controller, factory-gate]` |
| `required_approvals` | 1 |
| `apply_to_admins` | true |
| `block_on_rejected_reviews` | true |
| `dismiss_stale_approvals` | true |
| `protected_file_patterns`, `unprotected_file_patterns` | empty |
| `enable_status_check` | false |

`factory-merge` (created with the admin API, `POST /admin/users`, a random
password nobody keeps) is a `write` collaborator on the code repository
and nowhere else; its one token, named `factory-merge`, is
`write:repository` scoped to the code repository only (minted with admin
basic auth and `?sudo=factory-merge`) and lives in secret
`factory/forgejo-merge`, key `token`. Its merge is refused (405) until
an APPROVED review of sebastian, the controller or `factory-gate` is on
the head. The console submits a human's approval through the approver's
own OAuth token. A new push dismisses the approval. Its push
to `main` is refused (git: "Not allowed to push to protected branch main";
contents API: 403). It cannot read the infra repository (404).

`factory-gate` is the approver bot (ruling R59), made the same way: a
`write` collaborator on the code repository and nowhere else, on the
approvals whitelist and not on the merge or push whitelists. Its one
token, named `factory-gate`, is `write:repository` scoped to the code
repository only and lives in secret `factory/forgejo-gate`, key `token`.
It may approve a pull request, never merge one. A leaked gate token can
approve but not merge, and a leaked merge token can merge only what an
approver approved.

`factory-chat` is the project agent's own user: every Forgejo call of a
turn no member started (a wake) goes out as it, so the agent's bounded
funding and its answers work while no member is logged in. It is made the
same way, a `write` collaborator on the code and the infra repository
(the infra project has a chat too) and on none of `main`'s whitelists. Its
one token, named `factory-chat`, is `write:repository` and `write:issue`
scoped to those two repositories (Forgejo puts issues and comments under
the issue scope) and lives in secret `factory/forgejo-chat`, key `token`.
factoryd's trust gate hears its comments as a writer's, as a member's: an
answer to an escalation, a steering comment. A leaked chat token can
comment on, close and file issues on the two repositories. It can push any
branch but `main` carrying a workflow that Forgejo runs with the
repository's Actions secrets, and it can post commit statuses that the
checks trust. `factory-merge`, `factory-gate` and every human writer hold
the same two powers. It can never push to `main` or merge, and no Forgejo
review of its counts: an approval the project agent decides goes through
factoryd, and the merge gate's review carries it on the merge rule `auto`
only.

`main` of `sf/ai-software-factory-infra` is human-only (rulings 101a,
209, 239): push and merge whitelists `[sebastian, controller]`,
`apply_to_admins` true, `required_approvals` 0, so factory-admin, the bots
and every other writer are refused, and the console's Merge of a
new-project pull request works for both approvers.

`scripts/setup-factory-merge.sh` does all of this idempotently as
factory-admin: it first requires `controller` to be a writer on both
repositories (Forgejo silently drops a user without write from a
whitelist; `scripts/seed-secrets.sh` makes it one) and changes nothing
otherwise. Then, for each of the three bots, it makes the user and its
collaborations when they are missing, and keeps the token in the secret
while that token reads `main` of each of the bot's repositories and
carries exactly the bot's scopes; otherwise it revokes the older tokens of
the bot's name and writes a new one into the secret. No token and no
password goes on a command line: curl and kubectl read them from a pipe.
It PATCHes code `main`'s protection, and on infra `main` only the push
and merge whitelists, when a field differs. A run that finds everything
in place prints `no change` on every line. It prints both protections and
fails when a whitelist read back differs. factoryd reads the bots' tokens
at boot and does not start without them: run the script before a factoryd
that reads a new bot's token rolls, and after a new token, restart
factoryd. To replace a token, delete its secret and run the script. On a
rebuild the users, their collaborations and the protections come back
with Forgejo's database; run the script anyway, since the new cluster has
none of the secrets.

## Build cache

`k8s/platform/build-cache/` is the pull-request image builds' layer cache
(ruling 111): a `registry:3` Deployment and Service `build-cache:5000` in
namespace `forgejo`, plain HTTP, on a 20Gi `local-path` volume. Main CI
(the trusted dind runner) exports each image's BuildKit cache to
`cache/<image>:main` (`factory-gateway`, `opencode-worker`, `ci-runner`);
an untrusted PR runner pod copies it into a local OCI layout and streams
it to its build VM, which never reaches the cache itself. No credential
exists: the CiliumNetworkPolicy `build-cache-ingress` lets the
`forgejo-runner` pods use any method and pods in namespaces labelled
`factory.ai/ci=true` (factoryd's CI namespaces) only GET and HEAD, so a
write from a PR job answers 403; nothing else connects, and the registry
itself has no egress. The API's DELETE is off.

Each main run moves the tags and orphans the old cache's blobs: measured
at about 100 to 200 MB per main run that changes code (2026-09-28: 1.94 ->
2.15 GB over two runs, then 2.35 GB after a third; about 1.5 GB is the
three live caches). The CronJob `build-cache-gc` restarts the registry
daily at 03:30 UTC; its initContainer runs `registry garbage-collect
--delete-untagged` on the idle volume (strategy Recreate) and deletes
them, so the store holds the live caches plus one day's churn (a few GB
on a busy day). local-path does not enforce the 20Gi; the node's disk is
the hard limit.

The cache is disposable and nothing restores it: after a rebuild it is
empty, PR builds log "no cache" and build cold until the next main CI
run fills it. To empty it by hand, delete the PVC and the pod.

## The store of outside images (roadmap 203)

Every image the factory uses and does not build is a line of the code
repository's `upstream-images.txt`, pinned by its linux/amd64 digest.
The code repository's main CI copies each line the store lacks into
Forgejo's registry, org `upstream` (`scripts/upstream-copy`, its
`upstream` job, as factory-admin), at
`git.aisoftwarefactory.world/upstream/<the image's registry and path>`,
and every manifest here names the copy by its digest: the HelmReleases'
image values, the raw manifests, and the trusted runner's job image
(`ubuntu-latest`), which forgejo-runner pulls with the `forgejo-registry`
login mounted as its docker config (value `runner.pullSecret`). Org
`upstream` is public (Sebastian, 2026-10-16): a build's `ADD` and `wget`
fetch the store's packages without a login, its copies hold only
digest-pinned public bytes, and every other org and repository stays
private. Every pod that runs a copy names the pull secret
`forgejo-registry` all the same, which `scripts/seed-secrets.sh`
writes into `factory`, `platform`, `forgejo`, `k8s-infra` and
`flux-system`. The charts come from the store as well, each at one
version: an OCI chart as a copy by its digest (an OCIRepository with
`forgejo-registry`), an HTTP chart repository's archive from the store's
Helm repository (`k8s/platform/charts.yaml`, login `forgejo-charts`).
A line marked `bootstrap` is pinned by its digest at its upstream:
Forgejo, its database (CNPG, the barman plugin, cert-manager for the
plugin's webhook certificate), local-path and Flux run before the store
can serve, and a rebuild installs Forgejo's and cert-manager's charts by
hand from their upstreams by the list's digests. The nodes pull those
through registry mirrors of the store (`talos/patches.yaml`: docker.io,
ghcr.io, quay.io, registry.k8s.io, code.forgejo.org, factory.talos.dev),
Talos's own images by tag, which the copy carries at the list's digest,
Cilium by the amd64 digests the runbook installs it with: a pull the
store misses, or a store that is not up yet, falls back to the
upstream. `talos/registry-mirrors.sh <node>...` gives the nodes the
store's read login (RegistryAuthConfig, from
`factory/forgejo-registry-read`, never in a file here) and the mirrors,
without a reboot: after the seed's Forgejo pass, again when the seed
mints the token anew, and once on nodes generated before the mirrors.
`sh scripts/upstream-images-test/test.sh [list]` renders the platform
and every chart and checks each image and chart against the list (the
charts from their upstreams as the list pins them); without a list it
reads the store with `REGISTRY_USER` and `REGISTRY_PASSWORD`, checks
every reference is in it and renders the charts from it, as
`config-check` does on every push to main, with `scripts/helmrelease-check`.

A bump: the code repository's list first (its main CI copies the new
digests), then the references here; a reference whose copy is missing
leaves its pod in ImagePullBackOff. The copies live where the other
packages do: their blobs in bucket `aisoftwarefactory-forgejo`, their
rows in Forgejo's database, so a rebuild that restores both keeps them
(the dump skips package data; the CNPG recovery brings the rows). A
rebuild without them starts from an empty store: copy into it from a
workstation before Flux's first platform sync (Rebuild step 6), since
the trusted runner itself runs from the store.

## OpenBao SSH CA

Commissioned servers (task 53) trust one SSH CA in OpenBao, and the
factory gateway signs sandbox keys with it; factoryd reads the Forgejo site
admin's login there to register projects (ruling 212).
[k8s/platform/openbao/config.sh](k8s/platform/openbao/config.sh) sets it
up idempotently: the `ssh-client-signer` engine and its CA if missing,
role `factory-agent`, policy `factory-gateway-ssh`, the kv-v2 engine
`factory` if missing, policy `factoryd-forgejo-admin` (read of
`factory/data/forgejo-admin` only), `auth/kubernetes/config`, role
`factory-gateway` and role `factoryd` (ServiceAccount `factoryd` in
`factory`, audience `openbao`, policy `factoryd-forgejo-admin`, tokens of
1h). CronJob `openbao-config` in `platform` runs it
every 10 minutes and logs one line, `openbao-config: wrote <paths>` or
`openbao-config: no change`; a run while OpenBao is sealed fails and the
next one succeeds. It logs in as Kubernetes auth role `openbao-config`
(ServiceAccount `openbao-config` in `platform`, audience `openbao`), whose
policy reaches only the paths the script writes: reads of `sys/auth`,
`sys/mounts` and `ssh-client-signer/config/ca`, read and write on
`ssh-client-signer/roles/factory-agent`, and read and write on
`sys/policies/acl/factory-gateway-ssh`, `sys/policies/acl/factoryd-forgejo-admin`,
`auth/kubernetes/config`, `auth/kubernetes/role/factory-gateway` and
`auth/kubernetes/role/factoryd` with every parameter pinned by
`allowed_parameters` to the value config.sh writes. Anything else answers
403: another policy text, another ServiceAccount, audience or policy on
the gateway role, another `kubernetes_host`, a new CA, its own role and
policy. Unpinned, the identity could rewrite either policy to
`path "*"` and bind either role to itself (checked on 2.6.3, 2026-09-30:
both answer 403). The root token
never enters the cluster:
[scripts/openbao-config-bootstrap.sh](scripts/openbao-config-bootstrap.sh)
runs config.sh in `openbao-0` with the root token and then writes role
and policy `openbao-config`, the token passed over stdin and never
printed:

    set -a; . ~/repos/ai-software-factory/.env.seed; set +a
    BAO_TOKEN="$OPENBAO_ROOT_TOKEN" scripts/openbao-config-bootstrap.sh

Run it once on a new OpenBao (Rebuild step 7 has the fresh init); after
that the raft snapshot carries the role; run it again when its pinned
values change (the role `factoryd` of 2026-09-30 is one). The CronJob's policy only reads `sys/mounts`, `sys/auth` and
`ssh-client-signer/config/ca`, so enabling an engine or the auth method,
and generating the CA, is the bootstrap's job.

The kv-v2 secret `factory/forgejo-admin` (`username`, `password`) is the
Forgejo site admin factory-admin's login, written by
`scripts/seed-secrets.sh` from `FORGEJO_FACTORY_ADMIN_PASSWORD` with the
root token over stdin, never printed, and left alone when it exists and
names factory-admin (delete it to replace it); one that names another user
(a snapshot from before ruling 229 holds sebastian's) loses all its
versions and is written anew. factoryd reads it
at each registration into memory and never logs it; nothing else reads
it. config.sh generates a CA
only on OpenBao's exact "no default issuer currently configured" answer
and fails the run on any other read error: a second write to `config/ca`
makes a new CA the default and locks out every running agent server.

The engine at `ssh-client-signer` holds an ed25519 CA; its public key is
served unauthenticated at `/v1/ssh-client-signer/public_key`. Role
`factory-agent` signs user certificates, at most 30 minutes, extension
`permit-pty` only. A certificate opens one server (ruling 125): the
gateway signs for principal `resource-<row id>` of the task's own server,
and that server's cloud-init lists exactly that principal in
`AuthorizedPrincipalsFile` for root. OpenBao 2.6.3's `allowed_users`
takes no glob (`resource-*` refuses `resource-5`, with or without
`allowed_users_template`, verified 2026-09-28), so the role allows any
principal (`*`). Ruling 125 as amended: the binding is the server's
`AuthorizedPrincipalsFile` plus the gateway signing only for the task's
own server. Checked live on 2.6.3 (2026-09-28) with the gateway's login:
a request that omits `valid_principals` is signed for `unassigned`
(`default_user`), and one that sends `valid_principals=""` is signed with
no principals ("Principals: (none)"; `allow_empty_principals` false does
not stop it). sshd refuses both: neither matches the server's principals
file. The gateway always sends the server's principal.
Kubernetes auth role `factory-gateway` admits the `factory-gateway`
ServiceAccount in `factory` only, with audience `openbao` (the gateway
mounts a projected token with that audience; OpenBao reviews it with its
own ServiceAccount, bound to `system:auth-delegator` by the chart), and
its policy `factory-gateway-ssh` may only sign with `factory-agent`:
reading the role, longer TTLs and CA changes answer 400 or 403. The
role must carry `audience=openbao` whenever a gateway with that token
runs: OpenBao refuses its login otherwise, and commissioning and signing
fail. A change of the audience goes into config.sh and into the pinned
values of the bootstrap's policy in the same infra commit as the roll
that changes the token; run the bootstrap once for the new policy, then
check with one signing. OpenBao
is reached over plain HTTP inside the cluster: Cilium's WireGuard
encrypts pod traffic between nodes.
All of it lives in the raft storage, so the snapshot carries it.

## Image signing

Main CI signs every image it pushes (`factory-gateway`,
`opencode-worker`, `ci-runner`) by digest with the factory's cosign key
pair (roadmap 46), and factoryd's roller rolls only an image signed with
it: a changed image without that signature refuses the commit, and a
human card names each image and why. cosign is the code repository's
`Dockerfile.runner` download (stage `cosign`); the signature is a sigstore
bundle under the referrers tag `sha256-<hex>` beside the image in
Forgejo's registry, in no transparency log. The public half is
`k8s/cosign.pub` in the code repository; factoryd reads it through
ConfigMap `image-signing`, whose hashed name restarts factoryd on a new
key. The private half (the encrypted PEM `cosign generate-key-pair`
writes) and its password are OpenBao's kv-v2 secret `factory/cosign`
(keys `private_key`, `password`), written with the root token by the
script below and read by nothing in the cluster; the raft snapshot
carries it across a rebuild. `scripts/seed-secrets.sh` PUTs both on every
run into the code repository's Actions secrets `COSIGN_PRIVATE_KEY` and
`COSIGN_PASSWORD`, which only main CI's three image jobs read: agent pull
requests come from the bot's fork, and a fork's run gets no secret.
Without `factory/cosign` the script says `skipped` and main CI's sign
steps fail.
The images key is a second pair, kept apart so neither key can pass for the
other. The code repository's `project-image.yml` signs project images
(`sf/sandbox-<project>.<image>`) with it; factoryd verifies them with
`k8s/images-cosign.pub` (env `IMAGES_COSIGN_PUB`) and factory images with
the factory key. Neither key verifies the other's images. Its private half
and password are `factory/images-cosign`, which the seed script PUTs every
run as `IMAGES_COSIGN_PRIVATE_KEY` and `IMAGES_COSIGN_PASSWORD`; `--images`
makes it, with the same refusal, `--rotate` and read-back:

    BAO_TOKEN="$OPENBAO_ROOT_TOKEN" scripts/cosign-keygen.sh --images ~/repos/ai-software-factory-code

[scripts/cosign-keygen.sh](scripts/cosign-keygen.sh) makes the pair. Its
private half and password exist only in the tmpfs of a throwaway
container (read-only root, no network, no log) and go by pipe into `bao
kv put` in `openbao-0`; a second such container reads them back by pipe
and checks they make the public half, the one file it writes. It refuses
over an existing pair unless `--rotate`, and takes cosign from the code
checkout's `Dockerfile.runner`; `scripts/cosign-keygen-test/test.sh
<code checkout>` runs it against a throwaway OpenBao 2.6.3 in docker:

    set -a; . ~/repos/ai-software-factory/.env.seed; set +a
    BAO_TOKEN="$OPENBAO_ROOT_TOKEN" scripts/cosign-keygen.sh ~/repos/ai-software-factory-code

Then run `scripts/seed-secrets.sh` (`Actions secret COSIGN_PRIVATE_KEY:
201`, or `204` over an old one) and only then push `k8s/cosign.pub` to the
code repository: Flux applies it, factoryd restarts on it, and the push's
main run signs with the new key. A run signed with a key factoryd does not
hold is refused, and an empty commit on main starts a new run. A rotation
is the same with `--rotate` (a new version of `factory/cosign`); a fresh
OpenBao (Rebuild step 7 without a snapshot) has lost the pair, so make a
new one. Nothing verifies an image again once it is rolled, so a new key
leaves every pinned image running.

## Telemetry

SigNoz (`k8s/platform/signoz/`, chart 0.143.0) is the one telemetry
store. Two collectors of the `k8s-infra` chart (0.17.1, HelmRelease in
`k8s/platform/k8s-infra/`) feed its collector
`signoz-otel-collector.platform` on OTLP HTTP port 4319, theirs alone, from namespace
`k8s-infra` (Pod Security `privileged`: the agent mounts host paths,
which the cluster's baseline profile forbids elsewhere):

- `otel-agent`, a DaemonSet: host metrics (CPU, memory, load, disk I/O,
  read from `/proc`; the host's root filesystem is not mounted; the
  local-path user volume's fill, from statfs of the empty directory
  `/var/mnt/local-path-provisioner/.statfs` mounted read-only, so it sees
  no claim's data), kubelet stats (node, pod, container and volume, node
  network and filesystem included) and container log lines, read from `/var/log/pods` as uid 0
  without capabilities. It receives nothing (no OTLP receiver, no host
  port). Its ClusterRole reads pods, namespaces, nodes, volumes,
  ReplicaSets and Jobs, and the kubelet's `nodes/stats` and `nodes/pods`;
  no `nodes/proxy`, which would allow exec into any pod on the node.
  Log files it never opens:
  - the agent sandboxes `factory-agents-*` (CI included): an agent's
    transcript must not land in SigNoz;
  - the trusted runner `forgejo-runner` in `forgejo`: it echoes every
    job step's output, and a value a step prints without a mask would
    get a second copy here; Forgejo's Actions log keeps it;
  - SigNoz's own pods and `k8s-infra` itself: every insert would log
    lines that are inserted next.
- `otel-deployment`, one replica: cluster metrics from the Kubernetes API
  (pod phases, node conditions, Job counts, ...) and the Kubernetes
  events as logs (reason in attribute `k8s.event.reason`, namespace in
  `k8s.namespace.name`, the object in resource attributes
  `k8s.object.kind` and `k8s.object.name`, the message as body).

CiliumNetworkPolicies `otel-agent` and `otel-deployment` admit their
egress only to DNS, the API server, SigNoz's collector on 4319 and, for
the agent, its own node's kubelet (10250); neither admits ingress.

Every other sender (the projects' apps, factoryd, the gateway) sends OTLP
to the collector's 4317 or 4318, whose pipelines may not keep the
namespace the sender names: a project's rules and factoryd's alert
routing read `k8s.namespace.name`, so an app naming another namespace
would raise that project's alerts. These pipelines delete
`k8s.namespace.name` and `k8s_namespace_name` from the resource and from
every span, log record and data point, then `k8sattributes` sets
`k8s.namespace.name` from the pod the connection comes from (none for an
address no pod has); it keeps a value it finds, which is why the deletion
runs first. It waits for the pods and namespaces before the receivers
open (`wait_for_metadata`, 60 s), so a restarted collector takes nothing
it cannot name; a wait that times out leaves this build in its start with
its health check at 503 until the liveness probe restarts it. The running
collector's config, with what SigNoz's OpAMP has added, is
`/var/tmp/collector-config.yaml` in its container (`--copy-path`):
`kubectl -n platform exec deploy/signoz-otel-collector -- cat
/var/tmp/collector-config.yaml`. The pipelines of 4319 keep what the k8s-infra collectors
send, the namespace of what they measure. CiliumNetworkPolicy
`signoz-otel-collector` admits 4319 only from `k8s-infra`, the other
receivers' ports from the cluster, and the node.
`scripts/collector-namespace-test/test.sh` runs these pipelines, as the
HelmRelease writes them, in the pinned collector image against a stub
Kubernetes API: a pod's OTLP that names namespace `victim` arrives with
its own pod's namespace and no record naming one, an address no pod has
with none, and 4319 keeps what it is sent.

CronJob `signoz-objects` in `platform` (every 10 minutes, one log line
per object, `no change` once converged) writes into SigNoz what it keeps
on its volumes: factoryd's viewer account (secret `signoz-factoryd`,
role `signoz-viewer`; its login proves it, otherwise it is created or its
password reset), the webhook channel `factoryd` (POST to factoryd's
`/webhooks/signoz` with the basic auth of secret `signoz-webhook`, user
`signoz`), the dashboards in `signoz/dashboards/*.json` (by title),
the alert rules in `signoz/alerts/*.json` (by name; a file holds the rule
as SigNoz returns it, so an untouched rule compares equal), every
project's alert rules and the retention of traces, metrics and logs
through SigNoz's TTL settings API. Edits made in the UI are overwritten
on the next run.

The factory's own namespaces are projects' too (ruling 180):
`namespaces.yaml` labels `factory` for `ai-software-factory-code` (its
rules in that repository's `k8s/alerts`) and `platform` and `forgejo` for
`ai-software-factory-infra` (`signoz/project-rules`: a CNPG instance not
ready for 5 minutes, Forgejo's 5xx rate from its router log, and `Job
failed` bound to each; the two disk rules below), each with
`factory/objects: seed`, which keeps factoryd's admission policy out of
them. The infra project is on agents none: its alerts file human-lane
issues here; the label `noise` on such an issue when it is closed makes
the alert noise, any other close by a writer real.

A project's alert rules are project code (ruling 159): a ConfigMap in its
deploy directory labelled `factory/signoz-rules: "true"`, one rule per
key in SigNoz v0.143.0's `v2alpha1` shape. The job lists these
ConfigMaps in the namespaces labelled `factory/project` (ClusterRole
`signoz-objects`: list namespaces and ConfigMaps) and binds each rule to
its namespace: every builder query's filter becomes
`(resource.k8s.namespace.name = '<ns>' OR attribute.k8s.namespace.name = '<ns>') AND (<the rule's filter>)` (Kubernetes events carry the namespace as a log attribute only), the labels
`namespace` and `project` are set from the namespace, annotation `value`
carries `{{$value}}` unless the rule sets it, and every threshold
notifies the channel `factoryd` (`usePolicy: false`). Only builder
queries and formulas on metrics, traces and logs are taken, with filters
whose brackets and quotes close within themselves and no backslash, so no
filter reaches past the bound. factoryd files a firing alert as a `bug`
issue on the project's repository, found by the label `namespace`. The
bound rule's sha256 in annotation `factory_rule_sha256` tells an
unchanged rule; a rule no ConfigMap holds any more is deleted. A refused
rule (also a second key naming an alert already taken in the namespace)
is logged and its namespace's rules stay as they are; the run does not
fail on it, since the platform's `Job failed` alert is not the project's
to answer. Edits
made in the UI to a project's rule stay until its ConfigMap changes.
SigNoz's links (`ruleSource`, the webhook's `generatorURL`) name
`https://signoz.aisoftwarefactory.world` through
`signoz_alertmanager_signoz_external__url` in the HelmRelease. The run fails, and
so fires the alert below, when SigNoz records a retention set as failed
(it is set again) or still pending ten minutes on: a SigNoz restart in
the middle of a set leaves a row that SigNoz never ages out, and it
refuses every later set. Recovery: delete that row, then the next run
sets the TTL:
`kubectl -n platform debug -it signoz-0 --image=alpine --target=signoz`,
then `apk add sqlite && sqlite3 /proc/1/root/var/lib/signoz/signoz.db
"DELETE FROM ttl_setting WHERE status = 'pending'"`.

- Alert rule `Job failed` (ruling 160): the Job controller's Warning
  event `BackoffLimitExceeded` or `DeadlineExceeded` on a Job, a CronJob
  run included, at least once in the last 15 minutes, per namespace and
  Job name, severity `warning`. It clears by itself 15 minutes after the
  failure; a failed Job the CronJob keeps does not hold it. It notifies
  no channel: the rule's state in SigNoz is the signal, and factoryd's
  alerts endpoint counts it for a project namespace (a project's failed
  Job holds its promotion for those 15 minutes). The rule routes by
  notification policy (`usePolicy`), because SigNoz refuses a rule that
  routes to its thresholds' channels when they list none.
- Alert rules `Node disk above 80 %` and `Local-path volume above 80 %`,
  one per filesystem of a node: they read what no namespace holds, so no
  bound rule can; the label `namespace: platform` in their files routes
  them to factoryd, which files a human-lane issue on this repository.
  Node disk reads each node's EPHEMERAL
  (`/var`: the images, the pods' writable layers and emptyDirs, the
  factory caches) through kubeletstats `k8s.node.filesystem.*`, averaged
  over 5 minutes, per node. The images lie on it too, so the kubelet's
  `imagefs.available<15%` sets DiskPressure at 85 % and evicts pods; its
  image garbage collection starts at 75 % (`talos/patches.yaml`).
  Local-path volume reads each node's local-path user volume (every
  local-path claim on it: ClickHouse's disk `default`, the CNPG instance,
  OpenBao, ZooKeeper, SigNoz's database; a claim's size is no limit), a
  host path the kubelet reports no stats for, through the otel-agent's
  hostmetrics `system.filesystem.utilization` of mountpoint
  `/var/mnt/local-path-provisioner`, averaged over 5 minutes, per node.
- Alert rule `Chain poller stopped`, a platform rule like the two above:
  factoryd's gauge `factory.chain.poll_age` (seconds since the chain
  poller's last successful tick of a repository, computed at each
  30-second export, so a poller that stopped reads older at every export)
  above 60 for a repository over a 2-minute window. The poller ticks
  every 15 seconds; three ticks are 45 seconds, and the threshold is the
  next whole number of exports above, 60, so a healthy poller (age at
  most about 15) never reaches it and a dead one passes it within two
  exports.
- Retention: 7 days hot on ClickHouse's local-path volume, then moved to
  volume `s3` (disk `s3`, bucket `signoz-cold` on
  `fsn1.your-objectstorage.com`, prefix `data/`), deleted after 30 days
  (`HOT_DAYS`, `RETENTION_DAYS` in `signoz/objects.yaml`). A TTL change
  applies to parts written after it, so the first objects reach the
  bucket 7 days after a rebuild or a change. ClickHouse's
  `config.d/storage.xml` in the SigNoz HelmRelease defines the disk and
  the storage policy `tiered`; the key pair comes from secret `signoz-s3`
  through `include_from`, so it lands in no ConfigMap and no custom
  resource, and `hide_in_preprocessed` keeps it out of the preprocessed
  config on the data volume. Once the local volume is 90 % full, the
  oldest parts move to S3 early. The disk skips its access check, so
  ClickHouse starts even when the bucket is unreachable or the key wrong;
  parts then stay local, and a full user volume (the 20 Gi claim is no
  limit) stops every insert (ClickHouse's log names the failed moves).
  ClickHouse's system log tables lie on the local disk outside the
  storage policy: one day for `trace_log` and `processors_profile_log`,
  three for `query_log`, `part_log`, `metric_log`,
  `asynchronous_metric_log`, `aggregated_zookeeper_log` and
  `background_schedule_pool_log`, the chart's 3 to 30 days for the small
  rest (the HelmRelease: the operator's `clickhouseOperator.*.ttl`,
  `config.d/system_log.xml` for the tables it does not write).
  `zookeeper_log`, which the operator turns on, is off, and so is the
  memory profiler, the queries' (`memory_profiler_step` 0 in profile
  `default`) and the server's (`total_memory_profiler_step` 0), whose
  stacks were 95 % of `trace_log`. At the rates of
  2026-10-15 they peak near 5 GiB. ClickHouse takes a changed retention
  at its next start and renames the old table to `system.<table>_0`,
  which keeps its old TTL (none for `background_schedule_pool_log`); a
  log turned off leaves its table as it is: drop either by hand,
  `DROP TABLE system.<table>`. ClickHouse keeps the S3
  disk's metadata on the local volume, so after a rebuild the bucket's
  objects belong to nobody: the bucket's lifecycle rule (expire after 31
  days) removes them. For logs, SigNoz reports the retention from its own
  database, not from ClickHouse: if ClickHouse's volume alone is lost,
  the job says `no change` while ClickHouse runs its defaults. Then run
  the recovery above with `DELETE FROM ttl_setting`: the next run sets
  all three again.

The rebuild needs: bucket `signoz-cold` with that lifecycle rule, and
secret `signoz-s3` seeded (step 4) before the SigNoz HelmRelease rolls
ClickHouse. Everything else converges by itself.

## Cilium stays outside Flux

Cilium is the substrate Flux itself runs over, and its upgrades are
coupled to Talos (a Cilium upgrade rewrites the KubePrism endpoint
values). It is installed and upgraded imperatively alongside Talos and
deliberately not in the Flux tree, so no sync can break the network the
sync depends on.

## Home address change

Both firewalls admit the Kubernetes API (6443) and the Talos API (50000)
from the home address only: the Hetzner firewall (`home_cidr` in
`terraform.tfvars`) and the Talos `NetworkRuleConfig` `api-from-home` in
every machine config. When the home address changes, the controller is
locked out of both while git and the edge keep working. Recovery
(2026-09-29): set `home_cidr` to the new address and `tofu apply` (one
firewall change); then create a throwaway Hetzner server in the cluster's
private network (`node-mesh-tcp` admits 10.0.1.0/24) with its own SSH key
and a firewall for port 22 from the new address, copy `talos/talosconfig`
to it, and from there run `talosctl -e <node private ip> -n <same> patch
mc --mode=no-reboot --patch @patch.yaml` on each node, where the patch is a
`NetworkRuleConfig` document named `api-from-home` with the new subnet
under `ingress` (a strategic merge, so the old subnet may stay listed until
the next full apply). Delete the server, its firewall and its key.

Trap (2026-09-29, it cost the cluster): `hcloud_server.node` takes its
`user_data` from `talos/controlplane-*.yaml`, and Hetzner cannot change a
server's user data, so any edit of those files makes the next `tofu apply`
destroy and re-create the three nodes with empty disks. Never edit the
Talos config files while the cluster runs, and never apply a plan that
says anything other than "0 to add, 1 to change, 0 to destroy" for a
firewall change: read the "must be replaced" lines. Keep the home subnet
in the files equal to what the running nodes carry only through
`talosctl apply-config`, or leave the files alone until the next rebuild
and carry the subnet in `home_cidr` (`talos/README.md` regenerates the
configs from it).

Stage 3 outline) and in the ledger.
